# Moto G60 local full-stack demo

This is a loopback-only, disposable-data demonstration. It has no institutional OTP or verified payment. Do not expose Ktor to a public interface.

1. Prepare PostgreSQL 16 with **separate, disposable** `rit_canteen_dev` and `rit_canteen_test` databases. Copy `backend/.env.example` to ignored `backend/.env`, fill generated local credentials, `RIT_ENV=local`, `DEMO_SEED_ENABLED=true`, and keep `HTTP_HOST=127.0.0.1`. Do not commit `.env` or publish passwords.
2. From `backend/`, load the private environment (`set -a; source .env; set +a`), run `./gradlew clean build --no-daemon --max-workers=1`, then `./gradlew run --no-daemon --max-workers=1`. Confirm `curl -f http://127.0.0.1:8080/ready` returns 200.
3. Unlock the Moto G60 and authorize USB debugging. Check `adb devices -l`, run `adb reverse tcp:8080 tcp:8080`, and confirm it remains listed after any USB reconnect. The phone's `127.0.0.1:8080` now reaches the host Ktor process; USB attachment alone is insufficient.
4. From repository root build with `ANDROID_HOME=<installed-sdk> ./gradlew :app:assembleDebug --no-daemon --max-workers=1`, then `adb install -r app/build/outputs/apk/debug/app-debug.apk`. `-r` retains app data. Do not clear owner data unless separately authorized.
5. Open the sole RIT Canteen launcher, choose Login, and use a seeded persona from `backend/README.md` in the private local environment. Normal debug login calls Ktor; it does not accept local mock credentials. Seller/admin permissions derive only from `/auth/me`. If the backend is unavailable, reconnect and retry; do not switch to a fixture fallback.
6. Customer: choose Main Canteen, submit prepared food from the individual cart, and verify Orders shows the server ID with `DEMO_SAVED`, `demoOnly=true`, `paymentVerified=false`. Force-stop/relaunch and verify the same order returns. No kitchen acceptance or payment occurred.
7. Bulk: first configure the seller's weekly hours with the authorized owner/manager UI (`PUT /sellers/{id}/hours`); hours have no read-back endpoint, so avoid assuming the local editor reflects an existing DB value. Customer builds one-seller request totaling at least that seller's server minimum, chooses future pickup, submits, and sees the server request. Seller owner signs in, opens inbox, sends counteroffer and/or approves the current version. Customer signs in, refreshes, approves the same version; seller final approval produces `AGREED_AWAITING_PAYMENT`. This is unpaid, not pickup-ready. Reopen after app and server restart to confirm persistence.
8. For role checks, staff without `bulk.respond` must not act; North Counter owner must not read Main Canteen requests; admin is not a seller. Incorrect password, revoked session, offline backend, and stale quote version must show errors, never synthetic success.

The connected-mode feature matrix is in `ANDROID_BACKEND_SCREEN_MATRIX.md`. Favorites, notifications, support and analytics presentations are still local fixture UI in this checkpoint; do not present them as backend-persisted. The old local payment/QR simulator is not a server payment flow.

Troubleshooting: if `/ready` fails, check local PostgreSQL/Ktor logs without exposing secrets. If the app says backend unavailable, rerun `adb reverse` and keep the phone unlocked. If a normal bulk request is rejected for unknown hours, set server hours as the owner; do not bypass the backend rule. If a seller menu reflects prior edits, use the current server rows—the app must not reset a populated database just to restore seed visuals.

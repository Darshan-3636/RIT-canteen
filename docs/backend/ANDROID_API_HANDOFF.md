# Android API handoff — integrated local backend, no Android changes

Use this only for the later, separately authorized Android API-client milestone. The backend is a **loopback-only local demonstration**; do not replace the app's real-production trust boundaries with its debug payment simulator. When Netty actually listens on host port 8080 and the phone is USB-connected, run `adb reverse tcp:8080 tcp:8080`; the emulator/phone can then call `http://127.0.0.1:8080`. USB attachment alone does not forward the port. Never ship cleartext loopback settings, fixture credentials or mock privileges as production configuration.

Base: `/api/v1`; UTF-8 JSON; bearer header `Authorization: Bearer <opaque server token>`. Registration never assigns seller/admin authority; login response and `GET /auth/me` return live server-derived memberships/capabilities. Caller IDs are never accepted as authorization. Seller mutations recheck live capability inside their DB transaction; customer rows are scoped by bearer user; admin is independent of seller ownership. V1 errors have `{"error":{"code":"...","message":"...","details":null}}`. Unknown request keys are rejected. Money is integer paise; time instants are UTC ISO strings, while business dates/hours use `Asia/Kolkata`.

| Area | Mounted method/path | Essential request/result |
| --- | --- | --- |
| Readiness | `GET /health`, `GET /ready` | `200` status; `/ready` needs live PostgreSQL. |
| Identity | `POST /auth/register`, `POST /auth/login`, `POST /auth/logout`, `GET /auth/me` | Register `{fullName,email,password,affiliation,department?}` → `201` no token; login `{email,password}` → `200 {accessToken,expiresAt,user}`; logout `204` revokes token. |
| Profile | `GET/PATCH /me/profile` | Own record only; PATCH `{fullName?,affiliation?,department?}`. |
| Seller browse | `GET /sellers`, `GET /sellers/{sellerId}` | Four local fixture sellers when seed enabled. `openStatus=UNKNOWN` until real hours. |
| Catalog | `GET /sellers/{sellerId}/menu?query=&categoryId=`, `GET /sellers/{sellerId}/menu/{itemId}` | Local seed: 72 items, 18 per seller; published/visible only. Fields include `id,sellerId,name,description,pricePaise,kind,dietary,availability,published,orderingModes,imageKey,categoryId`. `imageKey` is logical (stable item ID), not a URL. |
| Seller catalog | `PATCH /sellers/{sellerId}/menu/items/{itemId}`; `PATCH /sellers/{sellerId}/menu/items/{itemId}/availability` | Requires `catalog.edit` or `availability.edit`; body fields are in `COMMERCE_API.md`. Staff with only `bulk.view` cannot edit. |
| Seller policy/calendar | `PATCH /sellers/{sellerId}/bulk-policy`; `PUT /sellers/{sellerId}/hours`; `PUT/DELETE /sellers/{sellerId}/closures/{localDate}` | Requires `hours.edit`; minimum defaults to 8 **combined units** per seller. Hours are unknown until explicitly set by authorized seller. |
| Individual demo history | `POST/GET /me/individual-demo-orders` | POST `{lines:[{itemId,quantity}]}` for Main Canteen prepared items only; `DEMO_SAVED`, `paymentVerified:false`, no kitchen/paid state. |
| Bulk customer | `POST /bulk/requests`, `GET /me/bulk/requests`, `GET /me/bulk/requests/{requestId}`, `POST /bulk/requests/{requestId}/customer-approval`, `POST /bulk/requests/{requestId}/withdraw` | POST requires `Idempotency-Key` and `{sellerId,lines:[{itemId,quantity}],pickupAt,specialPickupReason?}`. Approve/withdraw with `{expectedVersion}`. Cross-seller items/minimum/hours/closures are server-validated. |
| Bulk seller | `GET /sellers/{sellerId}/bulk/requests[/{requestId}]`, `POST /sellers/{sellerId}/bulk/requests/{requestId}/counteroffers`, `/seller-approval`, `/special-pickup-decision`, `GET /sellers/{sellerId}/pickup-schedule` | `bulk.view` reads; `bulk.respond` writes. Counteroffer body `{expectedVersion,lines,pickupAt,specialPickupReason?}`; approval `{expectedVersion}`; special decision `{expectedVersion,approved}`. Current revision, both approvals and separate special approval must agree. Schedule has no confirmed pickups without verified payment/operations. |
| Customer extras | `GET/PATCH /me/preferences`, `GET /me/favorites`, `PUT/DELETE /me/favorites/{seller\|item}/{targetId}`, `GET/POST /me/bulk-templates`, `GET/PATCH/DELETE /me/bulk-templates/{id}`, `GET /me/notifications`, `PATCH /me/notifications/{id}/read` | Favorites validate item through the real PostgreSQL Commerce port. Templates do **not** guarantee catalog validity on later submission. Notifications are `IN_APP_ONLY`. |
| Support | `GET/POST /me/support/tickets`, `GET /me/support/tickets/{id}`, `POST /me/support/tickets/{id}/messages`, `/escalate`; seller/admin ticket paths in `ENGAGEMENT_ADMIN_API.md` | Customer creates `{category,subject,message,sellerId?,requestReference?,clientRequestId?}`. Seller sees only tickets for its ID; admin sees platform scope. |
| Analytics/admin | `GET /sellers/{sellerId}/dashboard-summary`, `GET /sellers/{sellerId}/analytics/summary`; `GET /admin/overview`, `/admin/users`, `/admin/sellers`, `/admin/support/tickets`, `/admin/analytics/summary` | Seller needs `analytics.view`; admin needs live platform flag. Demo request counts are PostgreSQL-backed and labeled `DEMO_UNVERIFIED`. `verifiedRevenuePaise:null` and forecast insufficient until verified payments exist. |
| Deferred | `GET /sellers/{sellerId}/reports/export`; any payment-success/QR or real fulfillment endpoint | Export returns `501 EXPORT_NOT_IMPLEMENTED`; no server payment-success or pickup-redemption API exists. Never send client `SUCCESS` to mark paid. |

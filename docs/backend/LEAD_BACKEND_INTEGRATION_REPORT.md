## Runtime modules, schema and contract

`Application.kt` registers `registerCommerceRoutes(context)` and `registerEngagementRoutes(context, PostgresCommerceReadPort(context))` within the existing `/api/v1` router. The owner bootstraps Commerce fixtures only after Flyway/core seller + identity bootstrap and only for `RIT_ENV=local` with `DEMO_SEED_ENABLED=true`; a seed failure aborts startup and closes the pool. Production and test modes refuse demo seeding. The adapter reads active/published/visible `menu_items` for favorite lookup and groups real `bulk_requests` by seller/status and inclusive Asia/Kolkata business date for analytics. It has no fake in-memory counts, circular HTTP calls or revenue calculation. Customer, seller and admin routes use the contributor's live bearer/capability boundary; no client role or seller ID alone grants authority.

Actual Flyway history on the disposable app DB was `001,002,003,004,005,020,021,022,040,041,042`, every entry `success=true`, after clean and restart runs. Flyway checksum validation passed on repeated startup. The inherited foundation migration test already asserted the five core versions as a prefix, so there was **no** unnecessary test change. All applied migration files remained immutable; no V060 DDL was needed. Commerce's catalog FK couples `(seller_id,category_id)` to seller categories, and quote lines couple `(seller_id,item_id)` to actual menu items. Requests have indexed seller/status and customer paths plus per-customer idempotency uniqueness. Engagement favorites/templates/tickets/inbox and admin audit reference core seller/user tables with their declared CHECK/FK and unique constraints; there are no duplicated commerce tables or route collisions.

The backend demo fixture is `backend/src/main/resources/demo/catalog-categories-v2.tsv` and `catalog-items-v2.tsv`, extracted from `PreviewCatalog`/`CatalogArtwork` at the reviewed frontend head. A separate V1 12-row manifest is used only for guarded backfill. Fresh local databases produce **4 sellers, 72 unique item IDs, 18 each, 15 categories**, prices in integer paise, and `imageKey=id` with no fabricated photo URL. Live SQL returned `18/18/18/18`, 72 image-key matches and 2 `PACKAGED` Pantry items under `drinks`. The live API smoke checked every one of the 72 names/descriptions/prices/kinds/dietary/categories/availability/image keys against that manifest. Restart and seller edits are preserved. A legacy 12-item DB upgrades pristine rows (including `idli`, `north-lunch` and Pantry beverage category) and adds 60 rows while preserving changed seller values; old rows with customization may intentionally differ from pristine Android demo values. See [DEMO_CATALOG_PARITY.md](DEMO_CATALOG_PARITY.md). No database was silently wiped.

The frozen auth/profile shapes and error envelope remain unchanged. Detailed Commerce paths/DTOs are in [COMMERCE_API.md](COMMERCE_API.md); Engagement/Admin in [ENGAGEMENT_ADMIN_API.md](ENGAGEMENT_ADMIN_API.md); the definitive client-facing summary is [ANDROID_API_HANDOFF.md](ANDROID_API_HANDOFF.md). Expected errors actually exercised include 400 malformed/unknown fields, 401 revoked session, 403 missing capability/admin, 404 private or cross-seller record, 409 stale version/idempotency conflict, 422 unknown hours/minimum/wrong-seller item, and 501 export unsupported. Deliberately missing payment routes return 404; no client-provided success flag can mark an order paid.

## Limits and next handoff

This is **READY for a separately authorized local-demo Android API integration**, not ready for public deployment or real commerce. No Android client code was changed here. The backend uses local email/password fixtures, not verified college OTP; it lacks production TLS/deployment, abuse controls and verified seller onboarding. Individual records are `DEMO_SAVED`, not kitchen orders. `AGREED_AWAITING_PAYMENT` means a mutually approved current quote, **not paid/ready/delivered**. No payment webhook, trusted QR redemption, real inventory, SMS/push/email, XLSX export or verified revenue exists. Demo business hours were configured explicitly through the authenticated seller hours route in the disposable DB; no campus hours were asserted. The 24-hour quote expiry remains a contributor default awaiting owner policy confirmation. Android-bundled photos are illustrative and `imageKey` is not a URL.

Local run: start a private PostgreSQL 16 database on loopback, copy `backend/.env.example` to an ignored `.env`, set a generated `DATABASE_PASSWORD`, `DATABASE_URL`, `DATABASE_USER`, `RIT_ENV=local`, `HTTP_HOST=127.0.0.1`, `HTTP_PORT=8080`, `DEMO_SEED_ENABLED=true`; from `backend/` run `set -a; . ./.env; set +a; ./gradlew run`. For verified full tests create separate disposable test/fresh/legacy databases and follow `backend/README.md`. Android hookup later may use `adb reverse tcp:8080 tcp:8080` **only when** the local server really listens on that port. The later client must use server-issued identity and price/seller/availability data, keep local debug payment selectors out of server state, and not assume fixture `imageKey` is a hosted URL.

# Android phone acceptance (owner-run after approved deployment)

The Moto G60 passed earlier local backend-connected automated cart and V044 demo-lifecycle tests, including a cross-role customer → seller → customer round trip. **Hosted** independent-phone acceptance has not passed. Use a cloud-configured debug APK built from the same reviewed backend/client commit after V043–V046 are deployed; never enter private passwords into Codex output.

1. On Wi-Fi, cold-start the app, sign in with an authorized account and reopen after force-stop. Verify the same account, server profile, four sellers and 72-item catalog load. Repeat on mobile data; cold starts may take longer.
2. Open a seller and switch categories/search. Verify only that seller's products, prices and availability appear; detail and cart reflect the same items.
3. Add Main Canteen prepared food to the individual cart, change quantity, force-stop/reopen and relogin. Verify the same account's saved quantity and server-priced total; a second account must have a separate cart. Remove and clear, then confirm the empty cart persists.
4. With a disposable customer order, submit the individual cart once; verify one server order ID in history, `DEMO_SAVED`/unpaid labeling, and cleared cart after relogin. Retry after a network interruption only with a disposable test order. Choose a clearly labeled simulated payment outcome; no money is charged and `paymentVerified` must remain false.
5. With an authorized customer, save a favorite and preference, close/reopen, then remove them. Confirm server state, not a local-only “saved” toast; offline changes should show an error.
6. Create a disposable support ticket, reply and reopen it, and save/edit/remove a bulk template. Confirm data survives app restart and belongs only to that account.
7. For a disposable bulk request approved by the owner, review one-seller minimum and pickup policy. Save a draft, force-stop/relogin, and confirm seller, quantities, pickup time and instructions return. Check a second account cannot see it. If the deployed policy endpoint returns 404, expect “hours unverified” and stop policy acceptance. If deployed, check displayed hours/closure against server data. Verify a rejected/stale submission is not shown as successful.
8. With separate authorized Main Canteen seller credentials, verify the individual demo queue shows the same order ID, then simulate accepted → ready → completed. Refresh customer history and confirm each status. A seller at another counter and a non-responding staff member must not change it. Also check bulk counteroffer/approval without cross-seller access. No account should gain seller/admin access by choosing a role in the UI.
9. Open notifications and mark one read; reopen and confirm the server read state. In seller insights, check bulk-request counts/statuses against disposable persisted requests; revenue/report panels must not invent sales. Confirm the simulated payment outcome is never displayed as a real PhonePe payment, verified bank charge, QR pickup token or real collected order. Test direct-password signup only if the owner enabled the cloud-demo flag; the new account must have customer privileges only.

Do not test live write flows without the owner's explicit authorization and disposable test identities. Capture only redacted defects and steps, not tokens or passwords.

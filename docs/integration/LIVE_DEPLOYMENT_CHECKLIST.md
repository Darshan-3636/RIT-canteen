# Owner-controlled deployment checklist

Do **not** deploy this branch automatically. It adds Flyway V043/V044, account-scoped cart/checkout, demo payment and seller-demo status routes, plus opt-in cloud-demo customer signup. The last verified Render baseline did not have all of these routes; current deployed state was not reachable from this session. An APK containing the new cart client will show a request failure against an older backend, not silently save a local cart.

1. Review the branch diff, V043/V044 migrations and isolated PostgreSQL test report. Take a normal database backup before any hosted migration. Confirm no customer/order rows are truncated and no secrets or fixture passwords are being published in deploy settings.
2. Choose an approved merge/deployment sequence. Preserve the existing Render-bound branch until approved; deploy the backend first so Flyway applies V043/V044, then verify `/health`, `/ready`, `/api/v1/sellers`, and one seller's `/operating-policy` with read-only GETs.
3. Confirm the response contains the configured `minimumUnits`, `specialPickupEnabled`, timezone, actual hours and closures. A 404 means the new route is **not** deployed; do not present pickup policy as verified.
4. Confirm `GET /api/v1/me/cart/individual` returns 401 without a bearer. On a disposable authorized customer, check empty cart shape, versioned PUT/read-back, stale-version 409, and 422 for packaged or sold-out items. Check a second customer cannot see the first cart. Do not run these writes against a real customer's cart.
5. For the owner-approved direct-password demo signup, set `RIT_CLOUD_DEMO_SELF_SIGNUP_ENABLED=true` only on `RIT_ENV=cloud_demo` after accepting the risk that email and Student/Faculty affiliation are **not verified** and accounts are immediately active. This flag is false by default and invalid in production. Do not expose seller/admin registration or privately provisioned credentials. Add abuse controls and institutional verification before a real launch.
6. Build the cloud debug APK from the reviewed commit with `-PritCloudDemo=true -PritApiBaseUrl=https://rit-canteen-cloud-demo.onrender.com`. Verify the HTTPS origin and no local host, known passwords or debug hub are present in the APK. Deploy backend before distributing that APK; client/server versions must match.
7. On owner-controlled disposable customer/seller accounts only, verify signup, login, catalog, demo cart checkout, one stable order ID on retry and empty cart afterward. Simulate payment success on the customer order detail; verify `paymentVerified:false` and `demoPaymentOutcome:SUCCESS`. Seller should see the **same ID** and only authorized seller staff may move demo status through accepted, ready and completed. Customer history must reflect updates after refresh/relogin. None of these transitions authorize real food preparation or money collection.
8. Check server logs for authorization failures and Flyway version `044`. Never run destructive integration tests against Supabase. Keep admin creation and seller-owner provisioning private and owner controlled.
9. Keep real payment, QR redemption and operational fulfillment disabled until PhonePe Business provider integration, verified webhooks, business reconciliation, pickup authorization and tests are separately approved.

Rollback: retain the previously deployed immutable commit and its APK. V043/V044 are forward-compatible with existing demo rows; deploy the older application revision if needed, leaving the migrated database intact. Do **not** reset/migrate the private database from these instructions.
